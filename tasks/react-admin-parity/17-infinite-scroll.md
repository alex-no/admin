# Задача 17: infinite scroll (react-admin `useInfiniteGetList`)

> ## 🔧 Адаптація для `admin`: вердикт той самий, аргументи сильніші
>
> **Пропозиція — ❌ скасувати**, і в `admin` підстав більше, ніж у `allsto`.
>
> Конфлікти з наявним кодом фреймворку, які видно прямо:
> - `page` живе в URL через `useUrlFilters` (`DataListPage.vue:261`,
>   `useTableState.ts:93`) — при бесконечном скролі це поле втрачає сенс;
> - ключ `useListCache` — це повний URL із `page` (`:475`, `:224`), тобто кожен
>   «доскрол» стає окремим кеш-записом, і SWR перестає працювати як задумано;
> - `isAllSelected` (`:281`, `:177`) означає «всі на сторінці» — без сторінки
>   поняття зникає, а від нього залежить задача **08**;
> - `selected` скидається на кожному `load()` (`:460`) — доскрол або скидатиме
>   виділення, або муситиме перестати бути `load()`.
>
> Тобто це не «додати фічу», а «переписати чотири механізми ядра, які працюють».
>
> **Компроміс, якщо все ж треба:** кнопка «Завантажити ще» **на додачу** до
> пагінації, і лише як опція конфіга (`"loadMore": true` у `*.config.json`),
> вимкнена за замовчуванням.
>
> ---

## 🔴 Рекомендація: не робити

Задача описана для повноти пакету, але **рекомендація — відкласти або
скасувати**. Обґрунтування нижче; якщо рішення інше — специфікація готова до
виконання.

### Чому не варто

1. **Наша пагінація краща для адмінських задач.** `components/Pagination.vue`
   (143 рядки) уже вміє перша/остання/еліпсиси з розумним вікном навколо
   поточної (`pageItems`, рядки 83-130). Адмінський сценарій — «перейти на
   сторінку 47», «повернутись туди, де був» — infinite scroll не підтримує
   принципово.

2. **Ламає те, що вже працює.** Конфлікти з наявними фічами:
   - `useUrlFilters` тримає `page` у URL (`Users.vue:729-734`) — при infinite
     scroll поняття «сторінка» зникає, пряме посилання «сторінка 3» більше не
     має сенсу;
   - `useListCache` кешує по ключу `apiList?params` разом із `page` — при
     нескінченному списку ключ стає безглуздим;
   - задача **03** (prev/next по записах) рахує позицію як
     `(page - 1) * perPage + index + 1` — без сторінок формула ламається;
   - задача **08** (виділення всіх за фільтром) спирається на
     `allOnPageSelected` — «вся сторінка» перестає існувати;
   - `PER_PAGE_OPTIONS` до 250 (`Users.vue:722`) стає непотрібним, але його
     використовують у збережених фільтрах (`useSavedFilters` зберігає
     `perPage` — `Users.vue:841`).

3. **Немає користувача проблеми.** Infinite scroll вирішує «зручний
   перегляд довгої ленти на мобільному». Адмінка — desktop-інструмент для
   точкової роботи з записами, і скарг на пагінацію не було.

4. **react-admin теж не робить це дефолтом** — `useInfiniteGetList` там
   opt-in для окремих випадків, а `<Pagination>` залишається стандартом.

### Коли варто переглянути

- якщо з'явиться мобільна/планшетна адмінка;
- якщо якийсь конкретний список стане «лентою», яку читають підряд, а не шукають
  у ній (напр. `AuditLog.vue` або `ErrorLogs.vue` — журнали, які й правда
  проглядають хронологічно).

**Компроміс, дешевший за повний infinite scroll:** кнопка «Завантажити ще» під
таблицею **на додачу** до пагінації, тільки на журнальних сторінках
(`AuditLog.vue`, `ErrorLogs.vue`, `Analytics.vue`). Вона не ламає ні `page` в
URL, ні кеш, ні позицію запису — просто дописує наступну сторінку в кінець.
Якщо задачу все ж вирішено робити — робити **саме цей компроміс**, а не заміну
пагінації.

## Промпт для Claude Code (варіант «Завантажити ще»)

> Додай кнопку «Завантажити ще» під таблицею на журнальних сторінках адмінки, як
> додаток до пагінації, а не заміну їй.
>
> 1. **Тільки 3 сторінки**: `pages/AuditLog.vue`, `pages/ErrorLogs.vue`,
>    `pages/Analytics.vue`. Це журнали, які проглядають хронологічно.
>
> 2. **Пагінацію не прибирати.** Кнопка з'являється **під** таблицею, поруч із
>    пагінацією, і дописує наступну сторінку в кінець `items`. Пагінація
>    продовжує працювати як зараз (клік по номеру — заміна вибірки, не додавання).
>
> 3. **`page` в URL не змінюється** при «Завантажити ще» — інакше пряме
>    посилання перестане відтворювати те, що адмін бачить. Замість цього
>    тримати окремий `loadedPages` (скільки сторінок доклеєно) і **не** класти
>    його в URL.
>
> 4. **Скидати доклеєні сторінки** при зміні фільтра, сортування, `per_page` і
>    при кліку по номеру сторінки в пагінації.
>
> 5. **Не використовувати `IntersectionObserver`** (автопідгрузка при скролі) —
>    явна кнопка, щоб адмін контролював обсяг. Автопідгрузка на журналі з
>    десятками тисяч записів дає нескінченний DOM.
>
> 6. **Ліміт доклеювання** — напр. 10 сторінок; далі кнопка зникає з підказкою
>    «Використайте фільтр або пагінацію».
>
> 7. **`useListCache`** — доклеєні сторінки кешувати кожну під своїм ключем (як
>    зараз), а не одним великим масивом.
>
> **Не робити:** заміну пагінації, `IntersectionObserver`, розкатку на решту
> сторінок, зміну `useUrlFilters`.

## Технічні деталі

### Мінімальна реалізація

```js
// Доклеєні сторінки журналу. Свідомо не в URL: інакше пряме посилання
// відтворювало б випадковий обсяг доклеювання замість стабільного першого
// екрана. Пагінація залишається основним способом навігації.
const appendedPages = ref(0)
const MAX_APPENDED  = 10
const appending     = ref(false)

const canLoadMore = computed(() =>
  page.value + appendedPages.value < totalPages.value && appendedPages.value < MAX_APPENDED
)

async function loadMore() {
  if (appending.value || !canLoadMore.value) return
  appending.value = true
  try {
    const nextPage = page.value + appendedPages.value + 1
    const params   = buildListParams(nextPage)
    // ... fetch + items.value.push(...json.data)
    appendedPages.value++
  } finally {
    appending.value = false
  }
}

// Будь-яка зміна вибірки робить доклеєне безглуздим.
watch([() => page.value, perPage, sortItems], () => { appendedPages.value = 0 }, { deep: true })
```

⚠️ `appending`-guard обов'язковий: подвійний клік без нього доклеїть ту саму
сторінку двічі.

⚠️ `watch` на `page` мусить скидати `appendedPages` — інакше після «Завантажити
ще» × 3 і кліку на сторінку 5 адмін побачить сторінку 5 + три доклеєні від
попереднього стану.

## Scope & Non-Goals

**В scope (якщо задачу все ж робити):** кнопка «Завантажити ще» на 3 журнальних
сторінках, скид при зміні вибірки, ліміт доклеювання, guard від подвійного кліку.

**Поза scope:** заміна пагінації, `IntersectionObserver`, `useInfiniteGetList`-подібний
composable, віртуальний скрол, розкатка на решту 23 сторінки.

## FAQ

**Q: Чому це окрема задача, якщо рекомендація — не робити?**
A Щоб рішення було зафіксоване з обґрунтуванням, а не «забулось». У
[STATUS.md](STATUS.md) вона стоїть зі статусом-пропозицією «скасувати» — якщо
погоджуєшся, просто зафіксуй причину там і задача закрита.

**Q: А віртуальний скрол (рендерити тільки видимі рядки)?**
A Це інша задача й інша проблема — вона про продуктивність DOM при великому
`per_page`, не про навігацію. Якщо `per_page=250` реально гальмує — це окрема
задача, і вона не вимагає ламати пагінацію.

**Q: Чому саме `AuditLog`/`ErrorLogs`/`Analytics`?**
A Це append-only журнали: у них немає create/edit, їх читають хронологічно, і в
них найчастіше потрібно «подивитись ще трохи назад», не втрачаючи те, що вже
прочитав. Для довідників (`geography`, `catalog`) такого сценарію немає.
