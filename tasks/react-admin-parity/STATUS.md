| Шар | Зміна |
|---|---|
| Бекенд | `AdminStoController::create()` + `POST /api/admin/sto` у `routes.php`. Той самий allow-list `EDITABLE` і ті самі `FIELD_PERMISSIONS`, що в `update()` — інакше поле, закрите для редагування, можна було б проставити при створенні |

**Форма будується з конфіга, а не пишеться руками:** поля беруться з
`createFields`, а контроли — з того самого реєстру `cellTypes`, що малює комірки
таблиці. Тобто новий тип поля автоматично працює і в таблиці, і у формі, і
наступній сторінці форма дістається без коду.

Свідомі рішення:
- **`is_active` у `createFields` немає** — новий запис бере `DEFAULT 1` зі схеми.
  Інакше форма завжди слала б `false` (бо чекбокс за замовчуванням знятий), і
  кожен створений запис виходив би неактивним.
- **`select` ініціалізується першим варіантом.** Без цього список візуально
  показує перший пункт, а надсилає порожнє значення — і користувач бачить помилку
  про поле, яке «заповнене».
- **Помилки по полях показуються біля полів.** Для цього довелось поправити
  `utils/api.ts`: `parse()` кидав лише `message`, а тіло з `errors`/`fields`
  відкидав — у React показати помилку біля конкретного поля не було чим.
  Тепер помилка несе `status`, `errors`, `fields` (тип `ApiError`).

**Перевірено на живому бекенді** — 22 перевірки двома прогонами:
- права: `admin` має `sto.create`, `manager` ні; `manager` `POST` → **403**
- валідація: порожнє тіло → 400 з `errors` по обох полях; невідомий `sto_type` → 400;

- створення: → **201**, повертає запис з `id`, `phones` нормалізовані в масив із
  відкинутими порожніми, `is_active` збережено
- права на поле діють і при створенні: `admin` може задати `rating`
- наскрізь через конфіг: відтворив `blankForm()` ядра — порожня форма дає помилку
  саме на `name_uk` і **не** дає на `sto_type`; заповнена → 201; `address` доходить;

**Не перевірено — потрібен браузер:** вигляд форми в `BaseModal` на :5173 і :5174,

#### ✅ Прогалина 3 — іменовані bulk-дії + bulk-роут — зроблено 2026-07-31

| Шар | Зміна |
|---|---|
| Бекенд | `AdminStoController::bulk()` + `POST /api/admin/sto/bulk`. Дозволені дії — константа `BULK_ACTIONS` (`activate`/`deactivate`/`delete`) |
| Конфіг | `apiBulk` + `bulkActions[]` у `sto-registry.config.json`; контракт — у `shared/page-configs/README.md` |
| Vue | `DataListPage.vue` — `visibleBulkActions` + `applyNamedBulk()` |
| React | `useTableState.applyBulkAction()` + кнопки в `DataTable.tsx`; тип `BulkActionConfig` |
| Обидві сторінки | передають `apiBulk` і `bulkActions` з конфіга |

**Заодно закрито живий 404:** `StoList.vue:1688` слав `POST /api/admin/sto/bulk`,
якого в `routes.php` не було — масові дії легасі-сторінки не працювали взагалі.
Контракт роута зроблений під той запит, що вона вже шле (`{ ids, action }`), тому
вона запрацювала без правок; її `delete` через `commitOne` теж (перевірено, що
форма елементів `{id, row, index}` збігається).

Свідомі рішення:
- **Яке поле й на яке значення міняє дія — вирішує бекенд**, конфіг несе лише ім'я
  дії. Інакше конфіг (чи хто завгодно з DevTools) міг би задати довільну колонку —
  bulk-роут став би універсальним UPDATE в обхід `EDITABLE`.
- **Права на рівні поля діють і тут.** Дія з `field` перевіряє `FIELD_PERMISSIONS`
  так само, як `update()`/`create()`. Зараз ця гілка в демо не спрацьовує
  (`is_active` тонкого права не має), але без неї масова дія стала б обхідним
  шляхом до закритого поля — рівно та діра, яку закривала прогалина 1.
- **Undo немає навмисно.** `activate`/`deactivate` не деструктивні й скасовуються
  зворотною кнопкою; масове видалення лишилось на `apiDelete` з undo, і в
  `bulkActions` `delete` класти не треба (виконався б одразу й безповоротно).
- **Одним запитом, а не по одному на id** — на відміну від «Змінити поле…», яке
  шле PATCH на кожен рядок. Тому є стеля `BULK_MAX_IDS = 250` (= максимальний
  `per_page`) і дедуплікація id.

Заодно прибрано розходження рендерерів, що існувало до цієї прогалини: у Vue
`clearSelection()` скидає й вибране поле «Змінити поле…», а в React цей стан живе
в компоненті й не скидався — після будь-якої масової дії панель при наступному
виділенні відкривалась із попереднім полем. Тепер React скидає його при
порожньому виділенні (`useEffect` у `DataTable.tsx`).
