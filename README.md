# Admin — конструктор адмін-панелей

© 2026 Oleksandr Nosov. Ліцензія — [MIT](LICENSE).

Референсний проект адмін-панелі: список із фільтром і пейджингом, універсальне вікно
детальної інформації (плаваюче / докер справа / докер знизу), JSON-driven конфігурація
списків (без копіпасти однієї й тієї ж таблиці на кожній сторінці), inline-редагування
прямо в таблиці. Backend — Yii3 + SQLite, наповнюється з CSV і повністю скидається при
кожному рестарті контейнера (це фейковий бекенд для демонстрації та розробки, а не для
зберігання справжніх даних).

**Фронтендів два, на спільному бекенді:** основний на **Vue 3 + Vite** (`frontend/`) і
повний порт на **React 18 + TypeScript** (`frontend-react/`) — з тим самим набором фіч,
тими самими екранами і тим самим API. Vue-версія — еталон; React показує, що каркас
тримається на архітектурних рішеннях, а не на конкретному фреймворку. Детальніше — розділ 6.

Живе демо (логін `admin` / пароль `admin123` — або `manager` / `manager123`, щоб побачити
обмежені права):

- **Vue 3** — https://admin.4n.com.ua
- **React** — https://admin-react.4n.com.ua

Обидві демки працюють на одному бекенді й показують ті самі дані — їх можна відкрити
в сусідніх вкладках і порівняти екран в екран.

## 1. Як розгорнути проект окремо, щоб подивитися

Потрібен лише Docker Desktop (або Docker + Docker Compose на Linux).

```bash
git clone https://github.com/alex-no/admin.git
cd admin
docker compose up -d --build
```

Перший запуск займе кілька хвилин — фронтенд ставить npm-залежності, бекенд розгортає
Yii3 через `composer create-project` і сіє SQLite з CSV. Далі запуски швидкі.

Після старту:
- Фронтенд Vue 3 (dev-сервер з hot-reload): **http://localhost:5173**
- Фронтенд React (той самий набір сторінок, розділ 6): **http://localhost:5174**
- Бекенд напряму (для відлагодження API): **http://localhost:8080**
- Swagger-документація API: **http://localhost:5173/api/admin/doc**
- Логін: `admin` / `admin123` (суперадмін) або `manager` / `manager123` (обмежені права) —
  див. `backend/data/csv/users.csv`

Обидва фронтенди піднімаються одночасно і ходять в один і той самий бекенд, тож їх зручно
відкрити в сусідніх вкладках і порівнювати поведінку екран в екран.

Дані (СТО, країни, користувачі) лежать у `backend/data/csv/*.csv` — правите CSV,
перезапускаєте бекенд (`docker compose restart backend`) — нові дані підхоплюються
при наступному старті контейнера.

Окрім основної демки списку (**Дані → Реєстр даних**, `/data-registry` — вітрина каркасу
`list-framework`, описана нижче), у проекті є ще один блок демо-сторінок, що показує, що
той самий підхід (фейковий SQLite-бекенд, дані скидаються при рестарті) масштабується і
на складніші, не-табличні розділи адмінки — **Аналітика** (`/analytics`, `/analytics/stats`,
`/analytics/charts`) і **Логи помилок** (`/error-logs`, `/error-logs/stats`). Дані для них
генеруються процедурно при кожному старті контейнера (`backend/data/fake_analytics.php`), а не
беруться з CSV — там від природи великий випадковий time-series набір. Ці сторінки написані
не через `list-framework` (перенесені як є з продакшн-проекту AllSTO), тому як зразок
для розділу 4 орієнтуйтеся на `StoRegistry.vue`, а не на них. У детальній картці візиту
в Аналітиці є вкладка "Діагностика" (ping/traceroute/reverse-DNS/blacklist-check/HTTP-заголовки/
бан IP) — це **справжні** мережеві операції (`backend/src/Admin/Controller/AdminNetworkToolsController.php`),
а не заглушки; при перенесенні в інший проект їх варто або лишити як є (адмін-only,
IP валідується перед підстановкою в shell), або взагалі не переносити, якщо такий функціонал не потрібен.

Якщо потрібна ще одна dashboard-сторінка (карточки-зведення, топ-N розбивки, графіки) —
на відміну від списку+деталі (де є чистий зразок `StoRegistry.vue`), для цього типу сторінок
такого зразка немає навмисно: `Analytics*`/`ErrorLogStats.vue` — легасі-перенесення, а не
шаблон. [`.claude/skills/admin-dashboard-page/SKILL.md`](.claude/skills/admin-dashboard-page/SKILL.md)
розкладає, що з цих сторінок все ж варто переюзати (`BaseModal`, `ModalTabs`, чотири
SVG-чарти — `BarChart`/`PieChart`/`TrendChart`/`HourlyChart`, у кожного свій, несумісний
набір props), а що ні (ручні `fetch`+`authHeaders()` у кожній сторінці, самописна модалка
бана IP замість вкладеного `BaseModal`).

### Важливо про live-reload

На деяких конфігураціях Windows + Docker Desktop (особливо не системний диск) file-watcher
Vite не бачить правок файлів на льоту. Якщо після правки коду браузер не оновився — зробіть
`docker compose restart frontend` (для фронта) або `docker compose restart backend` (для бека,
PHP перечитується на кожен запит, але правки `composer.json`/додавання нового файлу в новий
неймспейс іноді теж потребують рестарту).

### Продакшн-варіант

`docker-compose.prod.yml` — єдиний контейнер (Apache+PHP), який віддає і зібраний
статичний фронтенд (`npm run build`), і API з одного й того ж процесу. Саме так
зараз розгорнуто на `admin.4n.com.ua`. Дивіться на нього як на приклад деплою за зовнішнім
reverse-proxy (у проді — хостовий Apache з Let's Encrypt).

## 2. Як інтегрувати цю адмінку в інший проект

Основна ідея проекту: більша частина коду адмінки — **не про конкретний продукт**, а про
перевикористовувані механізми. У будь-який новий проект переносяться саме вони, а бізнес-специфіка
(які сутності, які поля) описується конфігом.

### Що перевикористовується цілком

| Механізм | Де лежить | Що робить |
|---|---|---|
| Універсальне вікно деталей | `frontend/src/components/BaseModal.vue` + `frontend/src/composables/useModalWindow.js` | Три режими (floating / docked-right / docked-bottom), drag & resize, автозбереження режиму в localStorage, закриття по Escape — вбудовано, окремо додавати не потрібно. Контент — через slots (`#title`, `#subheader`, default, `#footer`), детальніше — 4.4. Це буквально **один і той самий** компонент у всій адмінці — жодна картка/форма (каталог, геодовідники, аналітика тощо) не тримає власної копії розмітки вікна |
| Каркас списку (список+фільтр+пейджинг+масові операції) | `frontend/src/list-framework/` | `DataListPage.vue` + реєстри типів (`filterTypes.js`, `cellTypes.js`) + `useRemoteOptions.js`. Колонки та фільтри задаються JSON-конфігом, а не хардкодяться в шаблоні. Вибір кількості рядків на сторінці та масові операції (чекбокси, bulk-редагування/видалення) — теж без додаткового конфігу, див. 4.2 |
| Селектор видимих колонок | `frontend/src/composables/useColumnPrefs.js` + `components/ColumnSelector.vue` | Показати/приховати колонки таблиці, налаштування в localStorage окремо для кожного `apiList`; `"hideable": false` у конфізі колонки закриває її від приховування |
| Порожній список із CTA | `frontend/src/components/EmptyState.vue` | Два стани замість одного сірого «Немає даних»: записів немає (→ кнопка «Створити», якщо є право) і фільтр нічого не знайшов (→ «Скинути фільтри») |
| Навігація «попередній/наступний запис» | `frontend/src/composables/useRecordNav.js` + `components/RecordNavigator.vue` | Стрілки й позиція «N / total» у заголовку картки деталей; перехід через межу поточної сторінки списку сам довантажує сусідню |
| Клонування запису | кнопка «Створити копію» в `DataListPage.vue` | Відкриває форму створення, попередньо заповнену значеннями вихідного запису — той самий `apiCreate`, що й для «Додати» |
| Розкривні рядки (row expand) | `frontend/src/composables/useRowExpand.js` | Стрілка розкриває додатковий рядок під основним із довільним вмістом (slot); кілька рядків розкриваються одночасно, скидається при зміні сторінки/фільтра |
| Skeleton замість спінера | `frontend/src/components/TableSkeleton.vue` | Рядки-заглушки на час завантаження замість повноекранного спінера — верстка не «стрибає» |
| Виділення всіх записів за фільтром | `frontend/src/composables/useRowSelection.js` | «Виділити всі N за фільтром» (не лише на сторінці) — масові дії йдуть як `{all:true, filters}`; бекенд рахує `COUNT(*)` і обмежує лімітом (`BULK_ALL_LIMIT`) |
| Undo для inline-редагування | `frontend/src/composables/useUndoableMutation.js` | Toast «Скасувати» на 5 секунд перед відправкою `PATCH`; черга дедуплікується за `id:поле`, незбережене флешиться через `beforeunload` + `keepalive` |
| Сайдбар фільтрів із лічильниками (facets) | `frontend/src/components/FilterSidebar.vue` | Групи значень із бейджами-лічильниками, які бекенд рахує окремим запитом (`?facets=поле1,поле2`) без урахування власного фільтра; клік одразу застосовує значення. **На відміну від решти рядків цієї таблиці — не підключено до `DataListPage.vue`/`StoRegistry.vue`.** У цьому демо є лише в окремій тестовій `pages/TestFacets.vue` (поза `menu.json`, backend-приклад — `AdminStoController`'s `?facets=`); щоб додати сайдбар на реальну сторінку списку, підключення робите вручну за її зразком, готового пропу на кшталт `expandable` для цього немає |
| Live-оновлення списку | `frontend/src/composables/useListPolling.js` | Тихе автооновлення раз на хвилину; пауза при неактивній вкладці, відкритій модалці або незбережених inline-правках |
| Зсув контенту при відкритому докері | `frontend/src/components/ListPageWrapper.vue` + `usePageLayout.js` | Докнуте вікно не перекриває список, а зсуває його |
| Синхронізація фільтрів/сортування/відкритої картки з URL | `frontend/src/composables/useUrlFilters.js` | Фільтри, сортування (зокрема мульти-колоночне) і відкрита детальна картка (id + активна вкладка) переживають перезавантаження сторінки і передаються в посиланні — див. 4.2 |
| Темна тема | `frontend/src/composables/useTheme.js` | `light`/`dark`/`auto`, перемикач у `TopNav.vue`, без «блимання» при першому завантаженні сторінки |
| Меню, кероване JSON | `frontend/src/config/menu.json` | Пункти меню + права доступу + (задел) ролі — без правки Vue-компонентів |
| Breadcrumbs | `frontend/src/components/Breadcrumbs.vue` | Ланцюжок «Головна / Розділ / Сторінка» будується з того самого `menu.json`, що й меню, — крихти й підсвічування активного пункту не можуть розійтися |
| Авторизація з dev-заглушкою | `frontend/src/composables/useAuth.js` | `VITE_MOCK_AUTH=true` — пускає з будь-якими даними, поки немає справжнього бекенда; `=false` — ходить у реальний `/api/admin/auth/*` |
| Багатомовність (i18n): українська/англійська/російська | `shared/locales/*.json` (спільні з React, alias `@locales`) + `vue-i18n` (`main.js`) | Перемикач мови — `components/LanguageSwitcher.vue` у `TopNav.vue`; локаль зберігається в localStorage (`admin.locale`), зміна без перезавантаження. Підпис у JSON-конфігах (колонки, фільтри, `menu.json`) — або звичайний текст, або ключ перекладу (`"table.name"`): рендерер сам розрізняє за наявністю крапки в рядку, окремого прапорця не потрібно |

Якщо цільовий проект на React — усе перелічене вище є і там, з тими самими іменами
й тим самим контрактом (див. розділ 6): `frontend-react/src/list-framework/`,
`components/BaseModal.tsx`, `hooks/useModalWindow.ts`, `usePageLayout.ts`,
`useUrlFilters.ts`, `contexts/AuthContext.tsx`, `shared/locales/*.json` + `i18n.ts`
(`react-i18next`). Кроки інтеграції нижче однакові для обох — відрізняються лише
розширення файлів (і, звісно, обирається лише одна з двох реалізацій, не обидві —
див. крок 0 нижче). Два місця, де контракт розходиться на практиці (область
видимості перекладів і механізм зсуву контенту при докнутому вікні) — розділ 6.

**І Vue, і React однаково залежать від `shared/core/`** (`hooks/useModalWindow.ts` →
`@core/modalWindow`, `contexts/AuthContext.tsx` → `@core/permissions` і так далі,
16 файлів на React-стороні проти 17 на Vue-стороні) — крок 2 нижче про копіювання
`shared/core/` стосується обох однаково, це не Vue-специфіка.

### Крок 0: оберіть один фронтенд

У цьому репозиторії дві реалізації живуть поруч навмисно (розділ 6 — це доказ
переносимості каркасу), але в *цільовий* проект переноситься **лише одна** — та,
що вже є (чи буде) саме у вашому проекті. Друга нічого корисного не додає, а тягне
за собою окремий toolchain, який ви ніколи не запустите:

| | `frontend/` (Vue 3) | `frontend-react/` (React 18) |
|---|---|---|
| Прод-залежності | `vue`, `vue-router`, `vue-i18n`, `bootstrap` | `react`, `react-dom`, `react-router-dom`, `react-i18next`, `i18next`, `bootstrap-icons` |
| Файлів у `src/` | 144 | 96 |

Якщо не впевнені — гляньте `dependencies` у `package.json` цільового проекту:
є `vue` — берете `frontend/`, є `react` — `frontend-react/`. Якщо фронтенду в
цільовому проекті ще немає — починайте з Vue-версії, вона тут еталонна (розділ 6),
при розбіжності поведінки правильною вважається саме вона.

Кроки нижче описані для Vue; для React — той самий порядок і той самий контракт,
міняються лише розширення файлів (`.vue`→`.tsx`, `.js`→`.ts`) і префікс
`frontend/`→`frontend-react/` (повний перелік відповідників — таблиця в розділі 6).

### Кроки інтеграції в існуючий проект

1. **Скопіюйте** у цільовий Vue 3 + Vite проект:
   - `frontend/src/list-framework/`
   - `frontend/src/components/BaseModal.vue`, `Pagination.vue`, `SortIcon.vue`, `ListPageWrapper.vue`
   - `frontend/src/composables/useModalWindow.js`, `usePageLayout.js`, `useUrlFilters.js`, `useAuth.js`
   - `frontend/src/config/menu.json` (як зразок структури, наповніть своїми пунктами)
2. **Скопіюйте `shared/core/` — обов'язково, незалежно від кроку 0.** Це не опція:
   майже все з кроку 1 — тонка Vue/React-обгортка навколо чистих TS-функцій із
   `shared/core/` (`useModalWindow.js` імпортує з `@core/modalWindow`, `useUrlFilters.js` —
   з `@core/urlState`, `useAuth.js` — з `@core/permissions`, сам `DataListPage.vue` — з
   `@core`; повний список — `shared/core/README.md`). Без цього каталогу й alias'а `@core`
   збірка впаде на `Failed to resolve import "@core/..."`.

   Залежностей це не додає — усередині `shared/core/*.ts` немає жодного імпорту з npm
   (`vitest` — лише у `*.test.ts`, їх копіювати не потрібно). Найпростіше — скопіювати
   всі `*.ts` файли (крім `*.test.ts`, `package.json`, `vitest.config.ts`, `node_modules/`)
   просто в `src/core/` цільового проекту й додати alias:

   ```js
   // vite.config.js
   resolve: {
     alias: {
       '@': fileURLToPath(new URL('./src', import.meta.url)),
       '@core': fileURLToPath(new URL('./src/core', import.meta.url)),
     },
   },
   ```

   (У цьому репо `shared/core/` навмисно лежить *поруч* із обома фронтендами, а не
   всередині одного з них, — саме тому, що на нього посилаються обидва. Якщо у вас лише
   один фронтенд, такої причини винести каталог назовні немає — кладіть просто в `src/core/`.)

   `shared/page-configs/` (і alias `@configs`) — **не обов'язковий**. Тут він існує
   з тієї ж причини, що й `shared/core/`: один і той самий JSON-конфіг сторінки читають
   обидва фронтенди, щоб не розходились. Якщо переносите лише один фронтенд, дублювати
   нема з чим — тримайте JSON-конфіги сторінок просто у своєму проекті (наприклад,
   `src/config/pages/`), без винесення назовні.
3. **Підключіть свій backend.** `DataListPage.vue` очікує від `apiList` відповідь вигляду
   `{ status, data: [...], pagination: { page, per_page, total, total_pages } }`,
   а `apiUpdate` — `PATCH /{id}` з тілом `{ поле: значення }`. Якщо у вашого API інший
   формат — або адаптуйте його під цей контракт, або поправте `load()`/`handleCellUpdate()`
   у `DataListPage.vue` під свій. Якщо хочете, щоб посилання на відкриту детальну картку
   (`?id=...`) працювало при прямому переході/перезавантаженні (а не лише при кліку по рядку
   вже завантаженого списку) — додайте також `GET {apiUpdate}/{id}` (один об'єкт), див.
   `AdminStoController::show()` і `StoRegistry.vue`'s `useUrlFilters({ detail: { id, onOpen } })`
   як зразок.
4. **Опишіть свою сутність** трьома JSON-файлами за зразком
   `shared/page-configs/sto-registry.{filter,columns,config}.json` (детальніше — розділ 4
   і `shared/page-configs/README.md`) — самі файли кладіть туди, де вирішили в кроці 2.
5. **Стилі.** Зараз використовується Bootstrap 5 — якщо в цільовому проекті інший UI-кит,
   компоненти `list-framework/filters/*` і `list-framework/cells/*` достатньо прості,
   щоб переписати розмітку під вашу дизайн-систему, не чіпаючи логіку в `DataListPage.vue`.

### Backend — за бажанням

Бекенд на Yii3 у цьому проекті — **демонстраційний** (фейкові дані, SQLite замість реальної
БД). Для інтеграції в реальний проект backend зазвичай береться не звідси, а пишеться під
реальну БД вашого проекту — важливо лише повторити контракт відповідей (див. вище) і, якщо
потрібен Swagger, — стиль анотацій `#[OA\...]` з `backend/src/Admin/Controller/*`
(атрибути пакета `zircote/swagger-php`).

## 3. Інтеграція за допомогою AI (Claude)

Цей проект спеціально спроєктований так, щоб інтеграцію робив не тільки людина руками,
а в першу чергу — AI-асистент (наприклад, [Claude Code](https://claude.com/claude-code)),
якому дали доступ і до цього репозиторію, і до цільового проекту. Вся механіка винесена
в зрозумілі, задокументовані, невеликі файли (JSON-конфіги, реєстри типів) саме для того,
щоб її було легко "прочитати" і повторити за аналогією — це рівно те, у чому AI-асистенти
особливо хороші.

### Найпростіший вхід: skill `admin-integrate` прямо в цьому репозиторії

Якщо не хочеться самостійно розбиратись у розділі 2 (особливо в кроку про
`shared/core` і alias'и) — найпростіший спосіб почати: відкрити Claude Code саме
в *цьому* репозиторії (з доступом і до цільового проекту поруч, наприклад
клонованого поряд) і попросити своїми словами, без жодного спеціального синтаксису:

> Додай цю адмінку в проект `<шлях або назва цільового проекту>`.

Спрацює skill [`admin-integrate`](.claude/skills/admin-integrate/SKILL.md) — він
ставить щонайбільше одне уточнювальне запитання (яку версію, Vue чи React, якщо
це не видно з `package.json` цільового проекту — крок 0 розділу 2 вище), копіює
точний набір файлів під обрану версію разом з обов'язковим `shared/core/` і сам
прописує alias `@core` у вашому `vite.config`. Він закриває рівно детерміновану,
"механічну" частину розділу 2 (кроки 0–2 — вибір фронтенду, копіювання файлів,
`shared/core`) — саме те місце, де найлегше щось забути чи переплутати вручну
(не той фронтенд, забутий `shared/core`, відсутній alias), і розраховано на
користувача, який не зобов'язаний знати наперед про ці деталі.

### Перенесення конкретної сторінки — вільний промт AI

Крок 3–5 розділу 2 (контракт API, ваша сутність, ваш UI-кіт) — це вже рішення під
конкретний проект, тому тут `admin-integrate` свідомо зупиняється і передає естафету
звичайному діалогу з AI:

1. Відкрийте Claude Code (або аналог) у цільовому проекті, до якого потрібно підключити адмінку
   (якщо `admin-integrate` вже відпрацював — базовий каркас у проекті вже є).
2. Дайте йому доступ так само і до цього репозиторію (наприклад, клонуйте поряд).
3. Попросіть приблизно так:

   > Вивчи `frontend/src/list-framework` і `frontend/src/components/BaseModal.vue`
   > у проекті `admin` — це каркас списку з фільтром/пейджингом і універсального вікна
   > деталей. Перенеси ці механізми в мій проект і підключи їх для сутності `<назва>`:
   > колонки `<...>`, фільтри `<...>`, детальна картка — докер справа. Дивись на
   > `frontend/src/pages/StoRegistry.vue` і `shared/page-configs/sto-registry.*.json` як на зразок, як
   > це поєднується на одній сторінці.

4. Для нестандартних елементів (свій тип фільтра, своя комірка таблиці) — попросіть
   зареєструвати новий тип через `registerFilterType()`/`registerCellType()`
   (див. розділ 4) замість того, щоб писати список руками з нуля.

AI добре справляється саме з цим видом роботи: контракт (JSON-схема, форма відповіді API)
чіткий і невеликий, а типових сторінок зазвичай багато і вони однотипні — тобто після
однієї показаної вручну інтеграції інші сутності AI може додавати за аналогією
майже самостійно.

**Чому саме ця частина не оформлена як skill (на відміну від `admin-integrate` вище
й розділу 4 — див. 4.5).** Тут інструкція для агента мала б наперед знати вашу
сутність, поля, UI-кіт цільового проекту — а це щоразу інше й не описується наперед.
`admin-integrate` навмисно зупиняється рівно там, де закінчується детермінована,
однакова для всіх частина (розділ 2, кроки 0–2) і починається та, що вимагає рішень
під конкретний проект. Цей розділ разом із шаблоном промта вище й є тим, що варто
скопіювати в `.claude/skills/` цільового проекту, якщо перенесення однотипних сторінок
у нього повторюється достатньо часто, щоб виправдати окремий skill саме там.

## 4. Як додавати нові сторінки та елементи

### 4.1. Проста сторінка (без списку)

1. Створіть `frontend/src/pages/MyPage.vue` (звичайний Vue-компонент, оберніть у `BaseLayout`
   або `ListPageWrapper`, якщо плануєте докер-вікно).
2. Додайте маршрут у `frontend/src/router/index.js`:
   ```js
   { path: '/my-page', name: 'MyPage', component: () => import('../pages/MyPage.vue') },
   ```
3. Додайте пункт у `frontend/src/config/menu.json` (в існуючу групу або нову):
   ```json
   { "label": "Моя сторінка", "to": "/my-page", "icon": "bi-star", "permission": "my.view", "roles": ["admin", "superadmin"] }
   ```

### 4.2. Список із фільтром і пейджингом (типовий випадок)

Візьміть за зразок `shared/page-configs/sto-registry.*.json` і `frontend/src/pages/StoRegistry.vue`.

⚠️ Конфіги сторінок лежать **поза** обома фронтендами — у `shared/page-configs/`, і
читаються обома через алиас `@configs`. Причина й контракт — `shared/page-configs/README.md`.
Раніше конфіг був у Vue-проєкті, а React тримав власну копію інлайном, і копії розійшлися.

1. **Колонки** — `my-entity.columns.json`, масив об'єктів:
   ```json
   { "key": "name", "label": "Назва", "type": "text", "sortable": true, "editable": true }
   ```
   `type` — береться з реєстру `frontend/src/list-framework/cellTypes.js`
   (`text`, `select`, `boolean`, `number`, `datetime`, `badge`, `link`, `image`, `phone-list` — останній зберігає масив рядків і
   форматує їх під "+38 (0XX) XXX-XX-XX", див. `cells/PhoneListCell.vue` і `utils/phone.js`
   як готовий зразок кастомного типу зі своїм форматуванням і E.164-нормалізацією при
   збереженні). `editable: true` вмикає inline-редагування прямо в таблиці (без
   `editable` — лише читання).

   Порожнє значення за замовчуванням показується як «—». Якщо порожньо саме по собі
   щось означає — задайте `"emptyLabel": "н.в."` (напр. порожній рік закінчення випуску
   моделі авто = «нині випускається»). Підтримують `text`, `number`, `select`, `badge`, `link`.

   `sortable: true` вмикає клік по заголовку колонки для сортування. Звичайний клік —
   сортування лише за цією колонкою; **Ctrl/Cmd+клік** — додає колонку до вже вибраного
   сортування (мульти-колоночне сортування, порядок кліків = пріоритет). Стан зберігається
   в URL одним параметром `?sort=key:ASC,key2:DESC` (через `multiSort` у `useUrlFilters`),
   на бекенд передається як `sort_by=key,key2&sort_dir=ASC,DESC` (список полів/напрямків
   у тому ж порядку). **Важливий нюанс:** якщо поле в БД зберігає код/id, а користувачу
   показується підпис (напр. `select`-колонка з `options`) — сортувати за сирим кодом
   неправильно, треба сортувати за словом, яке видно в таблиці. На бекенді для такого
   поля підміняйте `ORDER BY` на `CASE ... WHEN 'code' THEN 'Label' ... END` — приклад:
   `AdminStoController::sortExpr()` для колонки `sto_type`.

2. **Фільтр** — `my-entity.filter.json`, аналогічно, типи — з `filterTypes.js`
   (`text`, `select`, `checkbox`). Для випадаючого списку, що наповнюється з бекенда:
   ```json
   { "key": "country_id", "type": "select", "label": "Країна", "optionsUrl": "/api/admin/geography/countries", "optionsValueKey": "id", "optionsLabelKey": "name_uk" }
   ```
   Опції кешуються за URL — один і той самий довідник не завантажується повторно, навіть якщо
   використовується в кількох полях/сторінках. Кешуються сирі рядки відповіді, тому той самий URL
   з різними `optionsValueKey`/`optionsLabelKey` у різних місцях дає різні підписи, а запит лишається один.

   Коли підпис збирається з кількох полів — `optionsLabelTemplate` замість `optionsLabelKey`:
   `"optionsLabelTemplate": "{utc_offset} ({count})"` → `+03:00 (12)`. Плейсхолдер `{ключ}` береться
   з рядка довідника; відсутнє поле підставляється порожнім рядком.

3. **Конфіг ендпоінтів** — `my-entity.config.json`: `apiList`/`apiUpdate`/`apiDelete`,
   дозволи, кнопки дій у рядку (`detail`, `delete`, кастомні). Іменовані масові дії (кнопки
   в панелі bulk-редагування на кшталт «Активувати», а не «Змінити поле…») — окремий
   `apiBulk` + масив `bulkActions`; повний контракт (яке поле шле кожна дія й чому це вирішує
   бекенд, а не конфіг) — `shared/page-configs/README.md`, тут не дублюється.

   **Створення записів — окремий набір полів, без якого кнопки «Додати» немає взагалі**
   (буквально коментар у `DataListPage.vue`: «без `apiCreate` кнопки "Додати" немає»):
   - `apiCreate` — `POST`-ендпоінт створення.
   - `createFields` — масив ключів колонок, які показати у формі створення; контроли для
     кожного поля бере той самий `cellTypes`-реєстр, що й inline-редагування в таблиці.
   - `createPermission` — ховає кнопку «Додати» без права; бекенд перевіряє те саме повторно.

   Той самий `apiCreate` дає й кнопку «Створити копію» (розділ 2, «Клонування запису») —
   форма відкривається попередньо заповненою значеннями вихідного рядка, але лише полями
   зі списку `createFields`, решта значень рядка в копію не переноситься. Реальний
   приклад усіх трьох полів — `shared/page-configs/sto-registry.config.json`.

4. **Пейджинг, масові операції, селектор колонок і live-оновлення працюють без
   додаткового конфігу** — вони не описуються в JSON, `DataListPage.vue` вмикає їх завжди:
   - **Кількість рядків на сторінці** — випадаючий список (5 / 10 / 20 / 50 / 100 / 250,
     за замовчуванням 50) справа від пейджера. Як і сортування, синхронізується з URL
     (`?per_page=100`) через той самий `useUrlFilters`. Бекенд повинен вміти приймати
     `per_page` в `GET {apiList}` — див. `AdminStoController::list()` (там же максимум,
     до якого обмежується значення, — під свій бекенд можна зменшити/збільшити).
   - **Селектор видимих колонок** (іконка в тулбарі) і **live-автооновлення раз на хвилину**
     (кнопка-перемикач поруч, пауза при неактивній вкладці/відкритій модалці/незбережених
     inline-правках) — теж завжди ввімкнені, жодного пропу передавати не треба. Закрити
     конкретну колонку від приховування — `"hideable": false` у `columns.json` (розділ 2).
   - **Масові операції** — чекбокс перед кожним рядком (і «вибрати всі на сторінці» /
     «виділити всі N за фільтром» у заголовку, останнє — `useRowSelection.js`, задача 08).
     Щойно вибрано хоч один рядок, над таблицею з'являється панель: випадаючий
     список полів — **за замовчуванням** рівно ті колонки, у яких у конфігу стоїть
     `"editable": true` (нічого окремо перелічувати не потрібно); якщо треба звузити цей
     список (поле технічно `editable` для inline, але масово його міняти небезпечно/не
     має сенсу) — додайте в `config.json` `"bulkEditableFields": ["поле1", "поле2"]`,
     коментар біля відповідного коду в `DataListPage.vue` прямо називає це «серверним
     BULK_EDITABLE білим списком» — тобто це не лише зручність UI, а й межа, яку варто
     дзеркалити перевіркою на бекенді. А під випадаючим списком — **той самий** компонент комірки,
     що й для inline-редагування цього поля в таблиці (той самий `cellTypes`-реєстр, той самий
     контракт `field`/`modelValue`/`readonly`/`row`+`update:modelValue`) — новий тип UI під
     bulk-редагування писати не довелося. «Застосувати» шле **один** `POST {apiBulk}` з тілом
     `{ action: "update", field, value, ids }` (або `{ all: true, filters }` у режимі «всі за
     фільтром») — одна транзакція на бекенді, а не `PATCH` по черзі на кожен id (див. `apiBulk`/
     `bulkActions` у 4.2 п.3 і контракт у `shared/page-configs/README.md`). Кнопка «Видалити»
     з'являється лише тоді, якщо заданий `apiDelete` і в `actions` конфігу є дія `type: "delete"`,
     на яку в користувача є `permission` (та сама перевірка, що й для кнопки видалення в рядку).
     Вибір обмежений поточною завантаженою сторінкою (крім режиму
     «всі за фільтром») і скидається при зміні сторінки/фільтра/сортування/розміру сторінки.

5. **Сторінка** — тонкий `.vue`-файл, який просто передає ці три JSON у `DataListPage`
   (див. `StoRegistry.vue` цілком — там же приклад відкриття детальної картки в `BaseModal`
   по кліку на кнопку `detail`). Там же — зразок, як зробити так, щоб посилання на відкриту
   картку (і, якщо в картки кілька вкладок — на конкретну вкладку) переживало
   перезавантаження і годилося для передачі іншій людині: свій `useUrlFilters({ filters: { tab: activeTab }, detail: { id: detailId, onOpen } })`
   на рівні сторінки (окремо від того, що `DataListPage` вже робить для фільтрів списку) —
   `onOpen(id)` підвантажує запис через `GET {apiUpdate}/{id}` і відкриває `BaseModal`,
   `activeTab` синхронізується як звичайний фільтр. У `shared/page-configs/sto-registry.config.json` кнопки
   дій (`actions`) теж можуть відкривати одразу конкретну вкладку через `"tab": "..."`.

6. **Розкривні рядки й навігація «попередній/наступний запис» — це вже не JSON-конфіг,
   а props/слот прямо на сторінці**, поверх тих самих трьох файлів:
   - **Розкривні рядки.** `:expandable="true"` на `<DataListPage>` додає колонку зі
     стрілкою; вміст розкритого рядка — довільна розмітка в слоті `#expand="{ row }"`.
     Які рядки розкриті — `useRowExpand.js`, кілька одночасно, скидається при зміні
     сторінки/фільтра. Нічого в `columns.json`/`filter.json`/`config.json` для цього
     чіпати не потрібно.
   - **«Попередній/наступний запис»** у заголовку картки деталей — не вмикається сама,
     на відміну від пейджингу з кроку 4: сторінка власним `useRecordNav` (з поточним
     списком і позицією відкритого запису) і компонентом `<RecordNavigator>` усередині
     слота `#title`/`#subheader` картки; перехід через межу поточної сторінки списку
     сам довантажує сусідню.

   Зразок обох — `StoRegistry.vue` цілком (не окремий уривок, як для кроку 5).

### 4.3. Власний (кастомний) елемент фільтра або колонки

Якщо бібліотечних типів (`text`/`select`/`boolean`/`number`/`checkbox`) не вистачає:

```js
// у вашому коді ініціалізації (наприклад, main.js) або прямо в компоненті сторінки
import { registerCellType } from '@/list-framework/cellTypes'
import MyRatingCell from '@/components/MyRatingCell.vue'

registerCellType('my-rating', MyRatingCell)
```

Компонент повинен приймати props `field`, `modelValue`, `readonly`, `row` і емітити
`update:modelValue` — той самий контракт, що й у вбудованих `TextCell.vue`/`SelectCell.vue`
(дивіться будь-який з них як зразок). Після реєстрації просто вкажіть `"type": "my-rating"`
у JSON-конфігу колонки.

**Claude Code skill.** Різницю між одноразовим `type: "custom"` (через `customCellTypes`/
`customFilterTypes` на конкретній сторінці, без правки реєстру) і повноцінною реєстрацією
нового типу для всіх сторінок, а також обов'язкову стійкість компонента ячейки до `row: {}`
(bulk-редагування рендерить ту саму комірку без конкретного рядка) — формалізовано в
[`.claude/skills/list-framework-type/SKILL.md`](.claude/skills/list-framework-type/SKILL.md).
Головне, що він додає понад цей розділ: **реєстри — спільні для всіх сторінок**, тож новий
ключ додавати безпечно, а ось зміну поведінки вже існуючого типу варто починати з `grep`
по `pages/**/*.{columns,filter}.json`, хто ним уже користується.

### 4.4. Детальна картка (вікно)

Будь-яка кількість вкладок/полів — звичайна розмітка всередині `<BaseModal>`. Три режими
відображення, drag/resize, збереження розмірів у localStorage, закриття по хрестику/бекдропу/
Escape — вже працюють без додаткового коду. Головне правило: **у проекті немає жодної іншої
модалки, крім `BaseModal.vue`** — навіть для найпростішого вікна не копіюйте розмітку
`modal-window`/`resize-handle`/тощо, а обгортайте `<BaseModal>` і передавайте свій контент
через slots.

Мінімальний приклад:

```vue
<BaseModal
  v-model:visible="visible"
  storage-key="my-entity-modal"
  :default-width="700"
  :min-width="500"
  :max-width="1200"
>
  <template #title>
    <h5 class="mb-0">{{ mode === 'create' ? 'Новий запис' : 'Редагування' }}</h5>
  </template>

  <!-- звичайний контент — форма, деталі тощо -->
  <div v-if="saveError" class="alert alert-danger small mb-3">{{ saveError }}</div>
  <div class="row g-3">...</div>

  <template #footer>
    <div></div>
    <div class="d-flex gap-2">
      <button class="btn btn-sm btn-secondary" @click="visible = false">Скасувати</button>
      <button class="btn btn-sm btn-primary" @click="save">Зберегти</button>
    </div>
  </template>
</BaseModal>
```

Ключові props (повний список — `frontend/docs/BASE_MODAL_USAGE.md`):
`storageKey` (обов'язковий, унікальний ключ localStorage), `mode` (початковий режим,
за замовчуванням `'floating'` — довідник країн, наприклад, задає `'docked-right'`),
`defaultWidth`/`minWidth`/`maxWidth`/`defaultHeight`/`minHeight`/`maxHeight`,
`closeOnBackdrop` (вимкніть, якщо картка має власну логіку підтвердження закриття —
див. нижче), `headerClass` (напр. `"bg-primary text-white"` для акцентного заголовка).

Слот `#footer`: обгортка вже має `d-flex justify-content-between` — якщо кнопок лише
одна група (праворуч), перший елемент слота лишайте порожнім `<div></div>`, як у прикладі
вище. Слот `#subheader` — для панелі вкладок чи будь-чого іншого, що має сидіти між
заголовком і тілом на всю ширину (без відступів тіла); рендериться, лише якщо в нього
щось передано.

**Важливий нюанс при закритті.** Хрестик, клік по бекдропу і Escape закривають вікно
*всередині* `BaseModal` — вони не викликають жодну функцію вашої сторінки. Якщо при
закритті потрібно щось прибрати (скинути вибраний рядок, відхилити проміс, надіслати
подію `*-closed`) — не кладіть цю логіку у власну функцію `close()` (вона спрацює тільки
коли її викликають вручну, напр. кнопка "Скасувати"), а слідкуйте за переходом `v-model`
через `watch`:

```js
watch(visible, (val, wasVisible) => {
  if (wasVisible && !val) {
    // спрацює незалежно від того, як саме закрили вікно
    selectedRow.value = null
  }
})
```

Так само не потрібно вручну надсилати `modal-content-margin-change` (щоб сторінка
зсувалася при докнутому вікні) — `BaseModal` вже робить це сам.

Детальніше про всі props/слоти з прикладами — `frontend/docs/BASE_MODAL_USAGE.md`;
про сам композабл `useModalWindow.js` (якщо потрібно щось нестандартне поза `BaseModal`) —
`frontend/docs/MODAL_WINDOWS.md`.

## 5. Аудит змін і захист від одночасного редагування (заплановано)

На відміну від розділів 4.1–4.5, це — механізми, яких **у цьому демо навмисно немає**: обидва
переважно бекендові (нова таблиця + ручний виклик у кожному контролері, бо бекенд тут — сирий
PDO без ORM-хуків), а фокус цього проекту — фронтенд-каркас (`list-framework`, `BaseModal`).
Замість реалізації в самому демо, обидва оформлені як готові Claude Code skills із конкретним
планом (SQL-схема, приклад коду на основі `AdminStoController.php`, де саме показати результат
на фронтенді) — щоб додати в будь-який проект за потреби, не продумуючи підхід з нуля:

- **[`admin-audit-log`](.claude/skills/admin-audit-log/SKILL.md)** — журнал "хто/що/коли змінив"
  для запису: нова таблиця `audit_log`, helper для diff'а before/after, і вкладка "Історія"
  в картці деталей (або окрема сторінка перегляду, якщо треба фільтрувати по всіх сутностях одразу).
- **[`admin-optimistic-locking`](.claude/skills/admin-optimistic-locking/SKILL.md)** — захист
  від тихого перезапису, коли два адміни редагують один запис одночасно. Два рівні: дешева
  перевірка версії (`version`-колонка + `409 Conflict` при конфлікті — рекомендований варіант
  за замовчуванням) і, окремо, важча realtime-присутність ("зараз редагує Х") через
  polling-таблицю `edit_locks` або SSE — лише якщо першого рівня виявилося недостатньо на практиці.

Обидва skill явно перевіряють, чи є у цільовому проекті своя система міграцій (тут — немає,
схема живе прямо в `seed.php`), і радять писати нормальну міграцію замість інлайн-SQL, якщо
цільовий проект її має (наприклад, AllSTO — `www_app/migrations`, Yii-стиль `M<timestamp><Name>.php`).

### Як викликати

Так само, як і skill з розділу 4.5 — не потрібно вказувати назву файлу чи якийсь спеціальний
синтаксис. Skill активується автоматично, щойно запит по суті збігається з його `description`
(див. сам `SKILL.md` — там і прописано, на які формулювання він реагує). Достатньо в цільовому
проекті сформулювати завдання своїми словами, наприклад:

> Додай журнал змін для сутності `sto` — щоб було видно, хто і коли поміняв назву, тип чи статус.

> Два адміни іноді редагують один і той самий запис СТО одночасно, і другий тихо перезаписує
> зміни першого. Додай захист від цього.

Claude сам розпізнає, що це саме `admin-audit-log`/`admin-optimistic-locking`, підвантажить
відповідний `SKILL.md` і піде за планом звідти — включно з перевіркою, чи є в проекті міграції.

## 6. Друга реалізація фронтенду — React

`frontend-react/` — **повний порт** адмінки на React 18 + TypeScript + Vite, з тим самим
набором сторінок, тією ж поведінкою і тим самим бекендом. Локально — на
**http://localhost:5174** паралельно з Vue-версією, у продакшені —
**https://admin-react.4n.com.ua** (той самий контейнер і та сама SQLite, що й
у https://admin.4n.com.ua, розводяться за `ServerName`).

Навіщо це в проекті, який позиціонується як каркас: головна теза README — що більша частина
коду адмінки не про конкретний продукт, а про перевикористовувані механізми. Порт на інший
фреймворк — найчесніша перевірка цієї тези. Якщо каркас тримається на архітектурних рішеннях
(JSON-конфіг списків, реєстри типів комірок, єдине вікно деталей, контракт API), а не на
особливостях Vue, він має відтворюватись на React без переосмислення — і саме так і вийшло:
структура каталогів, імена файлів і контракти збіглися майже один в один.

**Vue-версія лишається еталоном.** При розбіжності правильною вважається поведінка Vue.

### Де реалізації свідомо розходяться

Не все, що доречно у Vue, доречно в React — кілька місць зроблено інакше навмисно:

- **Спілкування сторінки з модалкою.** У Vue сторінка відкриває картку через
  `window.dispatchEvent('show-analytics-details')`, а картка відповідає своєю подією. У React
  це звичайні пропси й стан — поведінка та сама, глобального каналу подій немає.
- **Джерело даних картки деталей.** В обох версіях картка бере дані з рядка таблиці, а не
  робить власний `GET /{id}` — інакше список і картка розходяться, якщо змінити значення
  в одному з них. У React додатково є зворотний зв'язок (`onRowUpdated`): інлайн-правка
  в таблиці одразу оновлює відкриту картку.
- **`useUrlFilters`.** Vue-композабл мутує передані рефи; у React стан належить компоненту,
  тому хук розділений на «прочитати початкове з URL» (`readFiltersFromUrl` для
  `useState(() => …)`) і «синхронізувати зміни в URL».
- **Гейт маршрутів за правами.** У React є (`RequirePermission.tsx`), у Vue роутер перевіряє
  лише наявність токена. Карта «шлях → право» будується з того самого `menu.json`, що малює
  меню, — щоб гейт і видимість пункту не могли розійтися.
- **Область видимості перекладів (i18n).** У Vue `useI18n()` Composition API за замовчуванням
  створює **локальний** екземпляр перекладів для кожного компонента — зміна мови в одному
  місці (наприклад, у `LanguageSwitcher.vue`) не оновлює інші, доки скрізь не вказано
  `useI18n({ useScope: 'global' })`. Пастка непомітна: компонент і далі показує переклад,
  просто застрягає на мові, яка була активна при монтуванні. У React `useTranslation()`
  (`react-i18next`) завжди глобальний, такої проблеми немає в принципі.
- **Зсув контенту при докнутому вікні.** У Vue кожна сторінка зі списком свідомо обгортається
  в `ListPageWrapper.vue`, яка сама слухає подію від `BaseModal` і зсуває **лише свій** вміст.
  У React той самий ефект (`usePageLayout.ts`) підключений один раз, глобально, у
  `layouts/BaseLayout.tsx` — застосовується до `<main>` одразу для всіх маршрутів, окремого
  `ListPageWrapper.tsx` немає. Звідси практичний нюанс: на конкретній React-сторінці **не**
  можна ще раз обгорнути її вміст у той самий `contentMargin` за аналогією з Vue — відступ
  застосується двічі, і таблиця зсунеться вдвічі далі, ніж треба, а при закритті докера
  вернеться не повністю. Заодно й назва самої `CustomEvent` відрізняється
  (`modal-content-margin-change` у Vue, `modal-margin-change` у React).
