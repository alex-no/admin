# Конфіги сторінок — спільні для Vue і React

Тут лежать JSON-конфіги сторінок `list-framework`, які читають **обидва**
фронтенди: `frontend/` (Vue) і `frontend-react/` (React).

## Чому не в `frontend/src/pages/`

Раніше конфіг сторінки `/data-registry` лежав у Vue-проєкті, а React тримав
**свою копію** того самого конфіга інлайном у `pages/DataRegistry.tsx`. Копії
розійшлися, і жодна перевірка цього не побачила:

- на колонці `rating` у React був `icon: 'bi-star-fill text-warning'`, у Vue не було —
  зірочка показувалась лише в одній версії;
- прапорці `hideable` (селектор колонок) додали спершу тільки у Vue, і в React
  можна було приховати `id` і назву;
- фільтри розійшлись **структурно**: `type: "text"` проти `'search'`,
  `placeholderOption` проти `placeholder`, `/api/admin/...` проти `/admin/...`.

Ні `vite build`, ні `tsc` такого не ловлять — це два різних файли, обидва валідні.
Тому конфіг винесений сюди: один екран = один конфіг, два рендерери.

## Як підключено

Обидва `vite.config` мають алиас `@configs` → цей каталог:

```js
'@configs': path.resolve(__dirname, '../shared/page-configs')
```

Вираз однаковий і в контейнері, і при локальному `npm run dev`:
у контейнері `__dirname` = `/app`, а `docker-compose.yml` монтує
`./shared:/shared`, тобто `../shared` = `/shared`.
Плюс `server.fs.allow` — інакше dev-сервер Vite не віддає файли поза своїм root.

Імпорт у сторінці:

```js
import columnsConfig from '@configs/sto-registry.columns.json'   // Vue
import columnsConfig from '@configs/sto-registry.columns.json'   // React — той самий рядок
```

## Контракт конфіга фільтрів

Свідомо один на дві мови, узгоджений 2026-07-30:

| Поле | Значення |
|---|---|
| `type` | `text` \| `select` \| `checkbox`. **Не `search`** — у React лишився приймати `search` як псевдонім лише для сумісності |
| `label` | підпис; використовується як fallback для порожньої опції select |
| `placeholder` | підказка в текстовому полі |
| `options` | статичні варіанти, **без** порожнього елемента |
| `placeholderOption` | порожній елемент select; якщо не заданий — `{ value: '', label: label ?? 'Всі' }`. Обидва рендерери додають його самі, тому в `options` його бути не має |
| `optionsUrl` | **повний** шлях, разом із `/api` (напр. `/api/admin/geography/countries`) |

## Контракт іменованих масових дій

`apiBulk` + `bulkActions[]` — кнопки в панелі масових операцій, кожна виконує
одну фіксовану операцію (на відміну від «Змінити поле…», де значення обирає
користувач). Без `apiBulk` кнопок немає взагалі.

| Поле | Значення |
|---|---|
| `action` | що піде на бекенд у тілі `{ ids, action }` |
| `label` | підпис кнопки; він же в повідомленні про результат |
| `icon` | клас bootstrap-icons, напр. `bi-check-circle` |
| `variant` | клас кнопки без префікса `btn-`; за замовчуванням `outline-primary` |
| `permission` | ховає кнопку без права; сервер перевіряє те саме повторно |

**Яке поле й на яке значення міняє дія — вирішує бекенд**
(`AdminStoController::BULK_ACTIONS`), а не конфіг. Тому конфіг не може змінити
довільну колонку: клієнт надсилає лише ім'я дії.

**Видалення сюди не входить.** Масове видалення працює через `apiDelete` з
undo — рядки зникають одразу, справжній запит іде після вікна «Скасувати».
Дія `delete` у `bulkActions` виконалась би одразу й безповоротно.

## Контракт CSV-імпорту

`apiImport` — кнопка «Імпорт CSV» поруч з «Додати». Без `apiImport` кнопки
немає взагалі. На відміну від `apiCreate`/`apiBulk`, окремого масиву полів
(`importFields` чи подібного) немає навмисно — майстер імпорту перевикористовує
той самий `createFields`: поля, які дозволено заповнювати при створенні запису,
дозволено заповнювати й при імпорті (той самий allow-list, ті самі
`editPermissions`/`FIELD_PERMISSIONS`, той самий `cellTypes`-реєстр для
приведення типу клітинки).

Майстер (Vue: `components/CsvImportModal.vue`, React:
`list-framework/components/CsvImportModal.tsx`) сам парсить файл і зіставляє
колонки на фронтенді — на бекенд іде вже готовий масив об'єктів:

```json
{ "rows": [{ "name_uk": "СТО «Приклад»", "sto_type": "service" }, { "...": "..." }] }
```

Відповідь — **не** all-or-nothing: рядок, що не пройшов валідацію, не зриває
решту файлу.

```json
{ "status": "success", "created": 3, "failed": [{ "row": 4, "errors": { "name_uk": "Назва обов'язкова" } }] }
```

`row` — індекс у масиві `rows`, який прийшов у запиті (0-based), не номер рядка
у вихідному CSV-файлі — зіставлення з номером рядка файлу робить фронтенд, бо
лише він знає, які рядки CSV відкинув парсер (порожні рядки) ще до відправки.
Ліміт рядків за один запит — серверна константа (`AdminStoController::IMPORT_MAX_ROWS`),
той самий принцип, що й у `BULK_MAX_IDS`/`BULK_ALL_LIMIT`.

## Правила

1. **Новий прапорець додається тут**, а не в сторінці. Якщо він потрібен лише
   одному екрану — це все одно конфіг цього екрану, а не код рендерера.
2. **Обидва рендерери мусять розуміти кожне поле конфіга.** Додав поле —
   перевір, що Vue і React читають його однаково; інакше повертається та сама
   проблема, лише всередині одного файла.
3. **`actions[]` без обробників.** JSON описує `type`/`label`/`icon`/`permission`/`tab`;
   що робить дія — вирішує сторінка (Vue — `@row-action`, React — `handler` за `type`).
   `type: "delete"` таблиця обробляє сама через `apiDelete`.
4. Файли читаються як звичайний JSON-модуль, тому **коментарів у них бути не може** —
   пояснення тримати тут.
