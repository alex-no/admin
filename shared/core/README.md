# Ядро — спільна логіка Vue і React

Чисті TS-функції без жодного імпорту з `vue`/`react` (і надалі — `@angular/*`),
які раніше були продубльовані окремо у `frontend/` і `frontend-react/`. Кожен
фронтенд і далі тримає свій стейт (`ref`/`useState`/майбутній Angular-сервіс)
і UI — ядро лише рахує, що покласти в URL/тіло запиту чи як відформатувати
значення, без жодної реактивності.

## Чому це тут

Дивись `../page-configs/README.md` — та сама причина: одна і та ж логіка,
задубльована вручну, розходиться непомітно для `vite build`/`tsc`.

## Модулі

Бізнес-логіка list-framework:

- `permissions.ts` — матчер прав (`'*'`, `'module.*'`).
- `listQuery.ts` — збірка `URLSearchParams` для запиту (page/per_page/сортування/фільтри).
- `sort.ts` — алгоритм цикла сортування (клік/ctrl+клік).
- `exportFormat.ts` — форматування значення колонки для CSV-експорту.
- `bulk.ts` — тіло bulk-запиту (`{ids}` або `{all, filters}`).
- `rowSelection.ts` — предикати/редʼюсери виділення рядків.
- `recordNav.ts` — позиційна математика «попередній/наступний запис».
- `remoteOptions.ts` — підстановка шаблону лейбла, `per_page` за замовчуванням.

Персистентність (усі — звичайний `localStorage`, не завʼязані на фреймворк):

- `columnPrefs.ts` — вибір видимих колонок таблиці.
- `savedFilters.ts` — іменовані пресети фільтрів.
- `modalWindow.ts` — режим/розмір/позиція плаваючого-докованого вікна.

Дрібні утиліти:

- `phone.ts`, `csv.ts`, `date.ts` — форматування.
- `urlState.ts` — мультисортування в URL (`?sort=key:dir,...`, окремо від
  `listQuery.ts` — той пише в тіло HTTP-запиту, цей у адресний рядок) і
  приведення значення фільтра з URL до типу за замовчуванням.
- `menu.ts` — пошук пункту меню за поточним шляхом (найдовший префікс).

Тост-стор і undo-мутації (headless store із підпискою — Vue загортає в `ref`,
React через `useSyncExternalStore`):

- `notifications.ts` — сам тост-стор (`notify`/`dismiss`/підписка).
- `undoableMutation.ts` — optimistic delete/update з undo, дедуплікацією за
  ключем і flush при unmount/закритті вкладки.
- `undoableDelete.ts` — простіша, більш рання версія того самого (без
  дедуплікації) — досі використовується окремо в багатьох сторінках поза
  list-framework. **Не реекспортується з `index.ts`** (колізія імен
  `deleteWithUndo`/`deleteManyWithUndo` з `undoableMutation.ts`) — імпортувати
  напряму: `import { deleteWithUndo } from '@core/undoableDelete'`.

## Реальні розбіжності, знайдені при переносі

Не просто копіпаста — під час звірки Vue/React рядок у рядок знайшлися і
поведінкові розбіжності. Канонічною щоразу стає поведінка Vue (проєктний
eталон), якщо явно не вказано інше:

- **`sort.ts`** — клік без модифікатора по спадній колонці при активному
  мультисорті: Vue скидав до одноколонкового `asc` саме на ній, React очищав
  сортування повністю. Тепер обидва — як Vue.
- **`urlState.ts`** — React писав у `?sort=` поточний (lowercase) регістр
  напряму зі стейту, але при читанні з URL завжди нормалізував до UPPERCASE
  (`'ASC'/'DESC'`) — після перезавантаження сторінки за посиланням із
  сортуванням іконка й `toggleSort` бачили "неправильний" регістр. Тепер
  канонічний регістр — lowercase, обидва боки узгоджені.
- **`modalWindow.ts` → `computeContentMargin`** — **не** та сама розбіжність,
  що інші: спершу здалось, що Vue правильно віднімає 24px (padding card-body),
  а React про це "забув", і компенсацію додали в обидва — тому React ховав
  скролбар таблиці під доковеним вікном (контент "заїжджав" на зайві 24px).
  Причина — різна DOM-структура: у Vue скролиться окремий
  `.list-page-wrapper` **без власного padding**, вкладений у `<main class="p-4">`
  (два різні елементи, тому компенсація потрібна); у React `<main class="p-4">`
  сам одночасно і скролиться, і має padding (один елемент, компенсація не
  потрібна). Тепер `paddingCompensation` — явний параметр: Vue передає `24`,
  React — нічого (default `0`). Урок: однакова назва змінної (`contentMargin`)
  і однакова формула не означають, що правильне значення теж однакове —
  залежить від оточення, яке ядро не бачить.

## Що свідомо лишилось поза ядром

- Рендер (таблиця/ячейки/фільтри/модалки) і сам стейт (`ref`/`useState`) —
  прив'язані до моделі реактивності фреймворка.
- Кешування довідників у `useRemoteOptions` — Vue кешує реактивні refs,
  React кешує проміси; це вже різні стратегії, не "той самий код".
- `utils/api.js`/`.ts` — React-версія помітно повніша (структуровані помилки
  з `errors`/`fields`, `apiUpload`, нормалізація шляху); уніфікація означала б
  міняти контракт обробки помилок по всьому Vue-фронтенду — окреме, свідоме
  рішення, не зроблене цим рефакторингом.
- `useUnsavedChanges` — API вже розійшовся за дизайном (Vue: `isDirty` +
  `markAsSaved/markAsChanged`; React: `confirmClose()` для підтвердження
  всередині застосунку), не лише за реалізацією — не "той самий код" під двома
  обгортками.
- `usePageLayout` — Vue і React слухають **різні** назви custom-подій
  (`modal-content-margin-change` vs `modal-margin-change`) від своїх версій
  `BaseModal`; уніфікація вимагала б змінювати й диспетчер події, не тільки
  хук. Vue-версія ще й додає CSS `transition`, якого немає в React.
- `menu.json` — дані (не логіка) вже розійшлися на одне поле (`note` у
  демо-пункті). `findMenuLocation` в ядрі приймає `menu` параметром саме тому;
  об'єднати самі JSON-файли в спільний — окреме рішення, не зроблене
  автоматично.

Не додавайте сюди нічого "про запас" — лише те, що вже реально продубльоване.

## Напрямок сортування: 'asc' / 'desc'

Канонічне представлення в ядрі — рядки нижнього регістру (`SortItem.dir`).
У Vue внутрішній стан історично був `'ASC'`/`'DESC'` (великими) — це нікуди
не змінювалось за межами `DataListPage.vue`/`useUrlFilters.js`, конвертація
в/з нижнього регістру відбувається локально на межі виклику `toggleSort` і
`parseMultiSort`/`serializeMultiSort`, щоб не займатись міграцією `SortIcon.vue`
та інших сторінок поза list-framework, які ASC/DESC теж використовують (через
окремий, однопольний `sorting`-режим `useUrlFilters`), але до ядра не мають
стосунку. Бекенд приймає обидва регістри (`strtoupper`), тож на API це не
впливає.

## Тести

Автономні, без залежності від жодного з фронтендів:

```bash
cd shared/core
npm install
npm test
```

## Як підключено

Обидва `vite.config` мають alias `@core` → цей каталог, той самий механізм,
що й `@configs` (див. `../page-configs/README.md`). React додатково резолвить
`@core/*` через `tsconfig.json` → `paths`, бо `npm run build` = `tsc && vite build`.

## Правила

1. Сюди йде лише те, що вже реально задубльоване в обох фронтендах — не
   абстрактна "майбутня перевикористовуваність".
2. Жодних імпортів з `vue`, `react`, `@angular/*` чи DOM-фреймворкових API
   (крім vanilla `Blob`/`URL`/`document.createElement` у `csv.ts` — це звичайні
   браузерні API, однакові в будь-якому фронтенді).
3. Нова функція — новий/розширений `*.test.ts` поруч.
4. Якщо переносите існуючу логіку — спершу звірте обидві копії (Vue і React)
   рядок у рядок; якщо вони розійшлися (як у випадку `sort.ts`), розбіжність
   лишити явним коментарем із поясненням, яка поведінка стала канонічною і чому.
